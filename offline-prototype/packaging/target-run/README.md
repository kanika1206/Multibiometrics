# Windows Phase 1 target-run pack — candidate, UNVERIFIED-ON-TARGET

The `payload/` directory now contains the complete assembled Windows x64 candidate: isolated CPython 3.12.16/Tk, pinned Python/native dependencies, app-local Visual C++ DLLs, FFmpeg/ffprobe and the specified face/ECAPA/Vosk models. Build/export environments are excluded. Static checks and development tests are not proof of Windows execution. The codec publisher's supported floor is Windows 10 22H2; exact target compatibility awaits the supplied machine details.

## One-sitting sequence
1. Transfer/extract `windows-target-run.zip` locally, check its published SHA-256, provide consented fixtures and physical administrator access. No download/install-from-network is needed. Record target details with `target-inventory.ps1`. It creates a new session ledger below LocalAppData/MultimodalOffline/acceptance-evidence/sessions.
2. Before trial intervals, configure and validate process/socket/blocked-egress monitoring using `NETWORK-PROCEDURE.md`. A packet-only trace is insufficient. Record tools/providers and sensitivity evidence; an unavailable monitor is a failed preflight, not an exemption.
3. Run `install.cmd` as administrator. It checks every inventoried input, installs to a NEW versioned Program Files directory, verifies installed hashes and assigns standard users read/execute only. It does not modify v1, install global Python/VC packages, migrate state or mark qualification. PowerShell execution-policy bypass is process-local. Launch the app as the standard target user.
4. Run installed `target-preflight.cmd`. It verifies the whole candidate, opens/closes Tk, tests DPAPI roundtrip, loads the actual local inference models, lists DirectShow devices and runs generated-input checks. Evidence goes to a unique acceptance run; disposable state is destroyed. This is preflight only, not acceptance. Use recorded device names for the UI. Check DPAPI cross-user rejection/key loss/ACLs separately.
5. Run installed `launch.cmd`: production must remain locked on the CANDIDATE manifest. Do not edit it to QUALIFIED to run tests.
6. Run installed `launch-acceptance.cmd`. It invokes the same UI/worker/inference/matcher/capture/store code and unchanged model/manifest bytes, with a fixed acceptance entry point and isolated evaluation state. No production switch exists. Use disposable identities and evaluation content only. At exit choose archive or destroy. Archive retains any consented plaintext research recordings.
7. Condition A: interfaces enabled, app and child-process egress blocked; monitor before launch through final descendant termination. Complete all rows in `templates/cases.csv`, including fresh enrollment/confirmation, restart, at least five verifications, wrong/missing/error factors, re-enrollment, deletion and faults. Every socket attempt, including blocked or loopback, fails.
8. Condition B: all external adapters/tunnels disabled, new equivalent evaluation state and fresh versioned install/copy where required; repeat the complete lifecycle and monitoring. Record/restore original firewall/adapter settings. Do not use remote-only access for this step.
9. For missing/corrupt-asset tests, use a separately copied disposable candidate. Do not alter the evaluated payload. Candidate-integrity rejection is a legitimate local fail-closed result; no downloader or fallback may run.
10. Run `WINDOWS-ACCEPTANCE.md` for DPAPI user binding, key loss, storage/crash/ACLs, timing, cancellation/suspend/cleanup and consent on/off. Retain raw evidence and fill the ledger per condition; failures are retained. New enrollment is three recordings plus confirmation; B0 stays single-recording. Preprocessing/ASR differences are separate from matcher differences.
11. To test full application restart after a crash, resume the same ACTIVE evaluation state with installed `runtime/python.exe -B app/resume_acceptance.py <run-id>`. No finalized run or production path is accepted. For a crashed/closed evaluation run, after killing its worker descendants, run installed `runtime/python.exe -B app/finalize_acceptance.py <run-id> --archive` or `--destroy`. Only valid evaluation run IDs are accepted. This never points at the production vault.
12. Review evidence, hash all artifacts and record the exact `candidate-inventory.json` SHA-256 plus asset-file-list hash. The acceptance template starts NOT_RUN; no script automatically marks PASSED. Production remains gated until separately reviewed qualification metadata and matching acceptance proof exist.

Normal production state is LocalAppData/MultimodalOffline/{vault,logs,transient,research-capture,acceptance-evidence}. Acceptance only creates acceptance-evidence/runs/<id>/state with its own versions of those directories. Completed runs cannot reopen; crash remnants stay isolated until explicitly finalized. Snapshot restoration is not prevented by challenge durability.

Remaining prerequisites from the user: target details/access and consented recordings. All Windows behavior is UNVERIFIED-ON-TARGET; latent platform/driver issues may require another build. No promise that tests will pass in one sitting.
